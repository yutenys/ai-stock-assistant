# 大盘核心数据刷新可靠性优化方案

> 已按本方案完成运行代码、测试和在线接口验收；实施记录见第6节。

日期：2026-10-22。代码基线：`df3b865831ca9cf8b11a95fcd7e924a98f573b6a`。

## 1. 目标与边界

解决“大盘核心数据部分更新失败”的真实原因，使行情、消息、板块资金分别反映自身的数据状态；同时阻断竞价、旧行情或缺失数据污染市场判断和推荐许可。

架构：沿用 Electron IPC、现有工作线程、缓存、请求封装和报告链路。增加必要的分组件质量摘要、跨线程新闻缓存和交易阶段标记；不重构整个 main.js，不增加依赖，不改变现有收藏和成交记录。

验收不以“不再出现警告”为准，而以失败可定位、可用数据继续展示、旧数据不冒充新数据、消息获取恢复及推荐输入可信为准。

1. `renderer.js / performMarketRefresh`：任何 `result.errors` 都显示“大盘核心数据部分更新失败”。
2. `main.js / fetchMarketOverview`：新闻失败、推荐计算失败、指数失败等共用errors；资金回退却主要写warnings。通知级别与数据组件不对应。
3. `fetchMarketNews`：金十、新浪依次请求，之后才尝试东方财富/Bing；新浪仅取第一页并筛选，空结果与传输错误混在一起。
4. `fetchMarketOverviewInWorker / finish`：每轮结束即终止线程；`marketNewsCache` 是线程内Map，下轮刷新无法复用其中的成功新闻和失败冷却状态。
5. `resolveObservationPhase`：09:15起归为intraday；`fetchTencentMarketSnapshot` 直接按报价统计涨跌停。09:16日志出现74涨停/137跌停，样本中多只open/high/low/volume/amount为0。这属于竞价报价观察，不能当连续交易确认。
6. `fetchMarketOverview` 的 `result.turnover ||= ...` 会把合法的0当缺失，并从无来源时间的简版指数补值。日志09:22约1.04万亿元与竞价时段存在口径疑点；尚未证明该数值具体来自哪一笔响应，实施时必须加字段来源核验。
7. `renderer.js` 每60秒刷新，包括非交易时间。工作线程生命周期导致组件内存缓存难以发挥作用。
8. `requestText` 使用socket空闲超时；若响应持续滴流，单次请求没有独立绝对截止计时器。大盘工作线程另有180秒总超时，不能替代组件预算。

## 3. 优先级与行为设计

### P0-A：分组件状态与可信显示

在现有结果增加 `components`：indices、breadth、turnover、limits、sectorCapital、news、recommendations、overseas。每项最少记录status、source、sourceObservedAt、fetchedAt、tradeDate、reason；计数型数据额外记录sampleCount/expectedCount，缺省为null。

状态使用fresh、partial、stale、empty、unavailable、not-applicable；empty表示请求成功但没有匹配内容，不能自动当作网络失败或“消息面中性”。保留errors/warnings兼容旧调用方，前端通知以组件状态汇总。

- 行情正常、新闻不可用：显示“大盘行情已更新；市场消息暂不可用”。消息卡显示原因、最近成功时间及重试入口。
- 资金回退：显示“板块资金暂不可用，当前显示历史参考（日期）”，不称“备用来源已切换”或实时资金确认。
- 部分指数/批次失败：明确“指数2/3项更新”或行情有效覆盖；保留旧值必须带旧时间。
- 全部核心行情失败：明确失败，保留最后成功画面及日期，不覆盖成0。
- 无适配字段的旧缓存显示待核验，不能默认fresh。
- 成功项、失败项、sourceTime、数据口径随缓存和报告一起保存；新一轮不能继承上一轮errors当新失败。

### P0-B：修复消息获取链路

1. 保留现有有效宏观主体过滤，不为了凑条数放入公司新闻或任意海外消息。
2. 新浪拆开“原始返回数、可解析数、时间有效数、范围匹配数”，记录过滤原因摘要。补齐“人民币兑美元中间价”等明确宏观语义，并加公司新闻反例。
3. 第一页匹配不足时最多读3页；时间窗口候选为最近24小时，休市/节假日按最近交易日调整并标明日期。每页先去重；窗口越界或已足够则停止。是否确有更多匹配内容须在实施阶段实测。
4. 金十与新浪可并发，最多2个新闻请求在途。总新闻预算建议12秒，单源至多一次短重试，仅用于连接重置/超时等可恢复错误；空结果不立即重试同一页，403/429遵守服务端冷却。
5. 在剩余预算内启动现有东方财富/Bing后备；不承诺此次未实测源已可用。首批可用新闻先显示，推荐使用冻结截止时点的数据，不将稍后消息回填旧推荐。
6. 利用现有磁盘缓存保存小型成功新闻集合和来源状态，线程启动读入。建议正常缓存2分钟；失败冷却按来源1/2/5分钟递增，上限5分钟。手动刷新只允许一次受控探测，不绕过429的Retry-After。
7. 缓存回退仍使用原publishedAt/sourceObservedAt；fetchedAt不能重写为“新闻新鲜时间”。过期新闻只展示参考，不参与实时消息加分。无新闻不等于无风险。
8. 独立实时新闻页共用获取/过滤/缓存修复，避免大盘恢复而消息页继续重复失败。

### P0-C：交易阶段及数据口径

保持既有 `observationPhase` 兼容，新增细分 `sessionPhase`，明确盘前、开盘竞价、开盘等待、上午连续交易、午休、下午连续交易、收盘竞价、收盘待确认、已核验收盘、休市。复用已有交易日历和模拟交易时窗；不得仅按电脑时间判断数据阶段。

- 同时核验来源时间和所属交易日。今天盘前返回昨天收盘，应标昨天收盘参考。
- 竞价价格允许展示，但涨跌停标记为“竞价触及涨跌停”，与连续交易涨跌停统计隔离。
- 竞价样本不写入连续交易广度峰值、恢复次数、板块资金持续性确认，不产生新的入场许可。
- 不通过“成交额为0”单条件剔除所有股票；停牌、竞价和未知值需分别识别。
- 使用带时间的指数数据；成交额的合法0保留为0，缺失为null。拒绝将昨日指数成交额补成今日全市场成交额。
- 全市场成交额与沪深指数汇总的覆盖范围分别标注，特别是北交所范围；日期、单位、范围不一致时不替补。
- 行情批次日期混杂/过期时计入无效覆盖，不因总数超过1000便认定完整可用。阈值基于已知目录和最近成功同范围快照制定，不能用失效目录作唯一真值。
- 历史错误竞价快照读取时按时间与数据状态排除，不删除原始记录、不覆盖历史报告。报告重生成另建修订。

### P1：刷新调度与有界等待

1. 复用现有并发刷新合并。核心指数/广度先出进度快照，随后各组件带状态更新；新闻失败不能清空成功行情。
2. 给新闻子流程和HTTP请求加真正的总时限/取消。到期取消底层请求、移除定时器和监听器，避免仅Promise超时但请求继续跑。
3. 首次上线保留手动完整刷新；自动刷新建议连续交易60秒、竞价60秒但只做竞价观察、午休5分钟、收盘后15分钟、夜间/休市30分钟。新闻独立按来源冷却；启动补报不因市场低频刷新被跳过。
4. 工作线程继续按现有方式释放；只跨线程保留必要的小型缓存，不改成长驻无限增长线程。
5. 日志每轮记录requestId、sessionPhase、各组件耗时/来源时间/缓存年龄/过滤数/错误码；重复错误汇总计数，避免每分钟重复写完整涨跌停列表。详细原始接口数据只留有限诊断样本。

## 5. 完成标准

1. 新闻失败时提示明确归属消息模块，不再笼统称核心行情失败；真正指数/广度失败仍有明确提示。
2. 可用新闻来源恢复时显示有效时间和可追溯链接；所有来源失败时可核验缓存回退，且不能加分。
3. 同一分钟重复刷新有合并与跨线程缓存证据，夜间不再每分钟扫描全市场。
4. 09:16的竞价报价不产生连续交易涨跌停结论、市场恢复确认或新的交易许可。
5. 指数/成交额/广度/资金各自日期、范围和时效可核验；0、缺失、旧值显示不同。
6. 收藏、模拟成交、历史报告保持完整；新报告能还原本轮各组件状态。
