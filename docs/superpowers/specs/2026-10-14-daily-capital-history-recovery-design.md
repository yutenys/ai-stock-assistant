# 完整历史逐日资金恢复与持续归档设计

> 日期：2026-10-14，第三版；2026-10-19完成工程链路落地。范围已由用户确认：上市以来全部历史；免费公开源的数据覆盖仍未通过完整验收。
> 目标：优先恢复吉华集团603980、光洋股份002708各自上市首个交易日至目标已结束交易日的全部逐日资金，再覆盖所有模拟持仓、收藏及推荐候选。资金真实性、日期完整性和界面响应必须同时保证。
> 约束：继续使用可合法访问的公开源，无付费账号；不安装无必要依赖，不修改网络安全设置，不绕过验证码/访问控制，不伪造缺失记录。不修改持仓、收藏、推荐权重或历史报告收益。

关联：[早期推荐与持仓复盘设计](../plans/2026-10-13-simulated-winners-and-position-management-design.md)、[推荐质量与隔夜风险设计](../plans/2026-10-12-recommendation-quality-and-overnight-risk-design.md)。本设计解决其资金证据缺口，不以资金接入成功代替策略有效性验证。

**15:07追加排查**：新取得两股各10条近期公开网页资金记录，原始响应已在本地隔离留存；日期为2026-09-22至10-13，金额取整且尚未交叉验真，不能替代上市以来序列或直接驱动评分。恢恢量化moneyflow索引实际为市场级北向等汇总，mootdxPlus历史日期只是近期返回值的本地筛选，均不能作为全历史恢复已可行的依据。详见上述核验记录第6节。

**2026-10-15上市首年文件续验**：匿名范围读取公开年度ZIP，取得光洋2014-01-21、吉华2017-06-15分钟行情样本；字段只有OHLCV，没有资金分档，故新增资金记录为0。另有公开仓库README声明2010至2026资金档案，但原始文件尚未取得，受限入口停止访问。课程数据需校内登录、近期五日协议也不能解决首年缺口。详见核验记录第10节；归档年份、样本日期和字段契约必须一起核验，不能把“全历史K线”误认成“全历史资金”。

**2026-10-19新增L2档案口径约束**：匿名取得QuantMind公开Parquet两个交易日、两股共4条派生资金样本，含原档案缺少的10月13日。6月12日总净额与Tushare吻合到两位小数，但光洋大单加特大单派生净额方向相反（-868.50与+384.5124万元）；故新源单列，不混入4693条，不自动补原序列。公开实现按逐笔成交金额分档，买入比例字段按笔数计算；仍需验证发布构建与单位转换。该源目录始于2018年，也不能解决上市早期缺口。详见核验记录第12节。完整性验收必须按来源及统计粒度分别计算，总净额一致不代表分档或所谓主力金额一致。

推荐采用“**冻结完整目标区间 + 公开历史入口/旧原始档案联合恢复 + 同源冲突核验 + 逐日覆盖验收**”。收盘增量留存作为防止再次丢失的并行工作，不能代替恢复过去。先恢复能取得的真实记录并逐日证明覆盖，再允许依赖这些数据的资金分析恢复；仍缺失的日期单列，不把错误提示隐藏当作修复。

用户已确认“完整历史”为**上市以来全部历史**。每股起点是经核验的上市首个交易日，终点是本次任务冻结的最近已结束交易日；不是买入日、最近一年或接口能返回的最早日期。买入以来、买入前60个交易日及最近10日仅是子区间验收，不缩小全历史分母。

三类交付必须分开：

1. 工程修复：不会重复轰炸失败源、不会卡住大盘、不会错算完整性、成功记录重启后不丢。
2. 数据恢复：具体代码、具体日期范围内的真实记录和缺口数量，不用“接口已接入”代替。
3. 策略启用：只有对应窗口完整且口径一致时，才恢复连续流入等判断；不自动提高分数或降低门槛。

### 2.3 本地已有数据不能直接拼成日资金

- `stockFundFlowHistoryCache` 是进程内Map；资金调用中未找到独立逐日磁盘档案写入。其他大盘缓存可能含局部资金，但不是可靠的日档案。
- 抽查10-14大盘缓存发现6个 `fundFlowPeriod`，均为真实多日汇总，没有逐日序列。
- 抽查10-12 r004、10-13 r003报告和09-18四条推荐账本，未发现可直接恢复的 `fundFlowPeriod.rows`；报告收藏上下文含资金摘要。这里只是限定文件/结构抽查，不能据此宣称所有备份、输入快照、其他日期账本均无数据。
- 旧日志的“实际日数、末日、来源”不是资金金额。不能从 `1/10日` 日志恢复净流入值。
- 本地收藏、模拟持仓的当前单日资金及3/5/10日总额，不能拆成每一日；也不能把今天数值回填昨天。

后续应先做受限、只读的档案恢复清单，而不是把全部巨型JSON一次读入内存。

## 3. 代码问题及影响

以下以本轮工作区代码为准；不覆盖现有 `main.js` 等未提交改动。

| 位置 | 问题 | 设计改动 |
| --- | --- | --- |
| `main.js/fetchDailyFundFlowHistory` | 每只股票顺序尝试三个入口；未见该链路的共享熔断/失败冷却/相同请求合并 | 按端点能力管理健康状态；共享进行中请求，失败源先探测再批量恢复 |
| 同上 | force绕过成功缓存；全部失败不写结果缓存 | force允许更新，不允许跳过冷却/并发上限；短期负缓存减少重复请求 |
| 同上 | 请求只表达days，最新若干日不能描述上市以来范围 | 扩展为明确上市起点及目标截止日；先读取本地覆盖，再分段补缺口 |
| 同上 | complete只按行数判定；达到行数即停止回退 | 核验目标日期、交易日缺口、重复、最终状态及来源口径；陈旧10行不是完整窗口 |
| `fetchSinaFundFlowHistory` | 从首个`[`到最后`]`截取后JSON.parse，业务错误/HTML缺乏明确分类 | 先检查响应类型与允许的JSON/JSONP结构，再校验业务码和行字段；禁止eval |
| `summarizeFundFlowRows` | 以数值大小猜元/万元，以比例绝对值<=1猜单位 | 改为经过样本核验的端点固定字段契约；单位不确定不生成可评分记录 |
| 两种历史summarize函数 | 净占比平均值、净额/流入流出合计可能被统一叫netRatio | 区分成交额净占比、买卖分项比率、日比例均值；不混为同一指标 |
| `mergeFundFlowSnapshot`及消费者 | 完整历史日期常被要求等于盘中tradeDate，易将昨日完整历史降为汇总；混合对象可同时带汇总与少量rows | 历史截止上一完整交易日、盘中资金单独存；按能力而非available布尔值消费 |
| `requestText`与重试函数 | socket空闲超时不是总截止时间，重定向/重试可累积耗时；错误主要是字符串 | 资金适配器增加可取消的总预算、响应体上限及结构化错误；不顺带重写全项目HTTP栈 |
| 主进程和market worker | 各自Map/限流不能天然跨线程共享；磁盘写入可能竞态 | 明确一个归档写入方和请求协调方，worker只传紧凑数据；不假设模块内Map跨线程有效 |

这些修复能消除应用端错误与放大效应，但不能保证第三方立即恢复历史服务。

## 4. 方案选择

| 方案 | 代价 | 结论 |
| --- | --- | --- |
| 继续加重试、换参数、安装抓取库 | 同一上游仍可能失败，放大请求，仍无历史留存 | 不采用；参数变更只在独立诊断中验证 |
| 把量价代理、多日汇总拼成逐日资金 | 输出完整但事实不成立，直接污染分析/回测 | 不采用 |
| **验证公开历史 + 检索原始旧档案 + 核验历史页面/合法导出 + 同源日档案** | 需要字段契约、证据与覆盖清单；旧历史仍有外部可得性风险 | 采用；先以完整区间为验收，再并行增量留存 |

不在本轮设计中强制引入Python、爬虫集群、数据库、付费服务或常驻后台。既有Electron/Node请求、原子JSON持久化、交易日历和任务进度足以实现第一版。

## 5. 数据源恢复与准入

### 5.1 先证明入口有效，再放进扫描

离线诊断与日常扫描分离。诊断固定小样本：603980、002708、600519、600704，加深市对照及一只有明确停牌状态的测试夹具；沪深实测与停牌单测分开，不拿普通股票无数据推断停牌。

每次诊断保存：端点、代码、请求窗口、运行时、起止时间、总耗时、HTTP状态、业务码、Content-Type、响应字节数、行数、首末日期、实际缺口及错误类别。错误响应只保留脱敏摘要/哈希，禁止记录Cookie或凭据。

1. 按公开页面实际参数调用东方财富历史入口；JSONP只剥离已知回调包装，不执行返回脚本。
2. 核验新浪当前公开入口是否仍提供服务。Node失败而浏览器显示真实表格时，才研究Electron原生网络栈的差异；二者都失败时停止把transport切换当已知修复。
3. 同花顺或其他公开源须先取得有日期、金额、口径的明细样本，再编写适配器。只有“资金流向”页面/搜索摘要/实时字段，不计准入成功。
4. 端点HTTP200但业务码失败、空HTML、仅实时单点均不算历史成功。同一provider多个域名不是多个独立来源。
5. 不随机扫域名/IP，不关闭证书校验，不复制私人Cookie或绕过访问限制；如确需登录/授权，停在该边界说明依赖。

**准入分层，不能相互替代**：发现页面只登记线索；取得原始日期/字段及口径后才可解析候选；契约核验且能在本机稳定获取后才进入在线采集；覆盖目标全部应有日期后才算该股该区间恢复完成。字段和单位须与同源页面/公开契约核验；在线适配器至少在两个分离时点测试并有一个对照成功。近10日可用不等于可恢复8月，另列最大历史深度、是否支持日期范围及分页。

两个目标分别验收。吉华暂不可得不能阻止保存已核验的光洋记录，光洋成功也不能使吉华或全市场被标为成功。历史页导入可成为一次性恢复能力，但不能据此声明在线接口稳定可用。

准入失败的provider保留诊断入口，不进入全市场每股票重复尝试链；当前访客源能力先标“偶有单日返回，历史深度未证实”，不得注册成90日历史源。

### 5.2 单日公开源也是有效建设路径

已有实时批量资金入口可以作为**未来日档案的采集候选**，但必须满足：

- 确认代码、资金交易日、来源口径、金额单位和采集时点；行情f124等时间戳若只是报价时间，不自动证明资金已结算。
- 收盘后抓取当天累计值并复核；该值是累计快照，不是区间增量。日内各次快照不得累加。
- 只有盘中记录时保存为intraday；只有收盘后累计快照且缺明确结算证明时为close-observed，不伪称provider-final。
- 后续真正历史源补回同日数据，保存修订与差异，不覆盖原始采集时间。不同日内/收盘/历史版本不能混用算连续性。

这一分支解决“从现在开始不再丢失已取得数据”，**不能逆向恢复从未抓到的8月数据**。

## 6. 最小数据契约与落盘

### 6.1 档案结构

新增紧凑的资金历史模块，复用 `lib/persistence.js` 原子写入和备份能力。建议路径：

```text
data/fund-flow-history/<provider>/<code>/<year>.json
data/fund-flow-history/recovery-manifest.json
data/fund-flow-history/provider-health.json
```

按代码、provider和自然年分文件保存日序列及来源修订引用，行内保留definitionId；全历史不按120日滚动裁剪，也不因退出收藏而自动删除。只将当前查询涉及年份/窗口载入内存，避免每次刷新整份上市以来档案。旧文件迁移必须验证后再切换索引，不删除原证据。

复用现有报告输入快照保存已冻结报告证据；不在推荐卡片、每次日志和持仓对象中重复嵌入整份历史。证据及用户数据留在本地，不加入Git。

单条规范记录：

```text
code, tradeDate, provider, definitionId, schemaVersion
mainNetAmount, largeNetAmount?, extraLargeNetAmount?, mainNetPct?, turnoverAmount?
amountUnit=CNY, ratioUnit=percent
phase=intraday|close-observed|historical-final|final-unverified
sourceObservedAt?, fetchedAt, firstObservedAt
origin=historical-api|historical-page|closing-snapshot|local-recovery|user-export
evidenceHash, evidenceLocator, revision, qualityFlags[]
```

问号字段可以缺，0为有效数据，缺失为null，不能互换。净流入为大单统计口径，不代表机构账户身份。estimated量价数据放原有独立分析字段，不写入真实资金档案。

证据索引另存原始URL/本地相对路径、文件哈希、JSON路径或表格行定位、采集方式、响应日期及取得时间；同一原始文件只存一份引用，不在每行复制正文。文件mtime和网页检索时间不是资金所属日期，也不能充当sourceObservedAt。仅有检索摘要/工具转换文本时登记线索，不伪称保存了原站完整响应。含用户账户字段的原文件留在原位置，不对外发送、不进入Git。

### 6.2 单位、比例和日期校验

- 元/万元、比例/百分数由provider定义，不按数值大小猜。0.3%与30%必须靠契约区分。
- 同源支持分项时检查 `mainNetAmount ≈ largeNetAmount + extraLargeNetAmount`，容差按该源显示精度，不设跨源万能容差。
- 有同口径有效成交额时，窗口净占比为 `sum(mainNetAmount)/sum(turnoverAmount)*100`。成交额不齐则窗口净占比unknown；日净占比简单平均可单独注明，不能当加权窗口净占比。
- 日期要是真实交易日且不晚于截止日；排除无效日期、重复日期和未来日期。停牌/上市不足分别解释，不生成假的0资金行。
- 不同源保持独立序列，优先选择覆盖目标窗口最多且口径合格的一条。缺口可以展示另一源的记录，但默认不拼成“同源连续10日”，跨口径资金金额不相加/相减。

### 6.3 历史完整性与盘中数据分开

查询参数明确为 `{code, startDate?, endDate, lookbackTradingDays?, includeIntraday}`。旧days接口内部映射为上一完整交易日的N日窗口；今天盘中资金独立附加，不要求历史末日等于今天。

结果明确包含：

```text
expectedDates, coveredDates, missingDates, suspendedDates
finalDailyRows, provisionalRows, aggregateWindows, intraday
status=complete|partial|unavailable|conflict
asOfDate, freshEnough, errors[], nextRetryAt
```

`complete`要求目标窗口每一日有合格同口径最终记录，或有经过核验的非交易/停牌解释；新股不足N日显示不足，不偷偷改成另一目标窗口。资格标志、可用日数、连续流入天数分别计算，不能用“有10行”代替。

若只有close-observed，显示“收盘累计快照，待最终核验”。第一版不以两次相等快照自动冒称最终数据；如后续接受该证据用于策略，需独立版本化准入规则，不夹带上线。

## 7. 历史缺口补采

### 7.1 吉华、光洋优先任务

首个任务起点已由上市披露核实：吉华2017-06-15、光洋2014-01-21，冻结截止2026-10-13；盘中10-14不算完整日。实施前仍须核对多年交易日历、停牌及证券身份，不得用当前缓存首日推断上市日，也不以确定上市日代替取得上市首年资金数据。

每次恢复任务生成不可静默变更的`rangeId`：记录证券身份、上市日期证据、目标起止日及日历版本。后续交易日以增量任务接续；不得边恢复边移动分母而无法完成验收。上市以来、买入以来、买入前60个交易日、最近10日分别计算覆盖。

全区间按自然年拆为可恢复任务，再依据已验证的provider单次窗口限制拆批。可以先完成买入以来以支持持仓复盘，但剩余上市早期年份必须继续列在任务中。逐年记录预期日数、合格行、冲突、缺失、来源可追溯最早日及停止原因，重启只补未完成分段。

多年历史须核验证券更名、代码/上市地变更和长期停牌；不得只按名称拼接，也不将更名前记录排除。供应商尚未开始采集的早年、原始逐笔数据不可得等情况属于真实历史缺口，不是休市，不能从验收分母中删除。不能用普通分笔成交重算并冒充供应商主力资金，除非完整订单分类证据和同口径可复现方法另行验证。

1. 先用现有交易日历和个股有效K线核对期望日期，分开记录休市、停牌与数据缺失；日K只能帮助核验交易活动，不能生成资金值。
2. 在已有缓存、报告输入、推荐账本、备份内只读检索有日期和金额的真实记录。分文件流式读取；大型JSON复用现有离线/worker读取方式，不在主线程一次加载几百MB。
3. 原始来源、金额单位、日期、最终状态可核验才入库；只剩资金摘要/净流入天数的记录不展开成日线。未知标记、estimated冲突进隔离列表待核验。
4. 对缺口调用已准入历史源，按其实际最大深度/分页规则补采。源不支持日期范围时不能假装传start/end就能回到8月；公开历史窗口已滚走则标unsupported-range。
5. 每批原子落盘并更新manifest；关软件后停止，下次启动续补，成功日期不重复全量拉取。
6. 输出逐股表：期望日数、合格日数、暂存快照日数、缺失日期、来源、下次重试时间、仍需外部条件。两个代码分别验收，不只展示总体成功率。

后续队列：所有模拟持仓与全部收藏去重、当前候选、其余研究股票。已移除但被报告/原计划引用的历史不从评价集合删除。采集优先级不能改变策略回测的固定样本。

### 7.2 不能采用的恢复方式

- 3/5/10日汇总不能唯一确定每个交易日；相邻滚动总额相减也不是某天净流入。即使可做数学估计，也不能写成原始资金。
- 净流入和成交额是不同统计量；内外盘差、K线位置、换手率、龙虎榜或融资余额不能代替逐日主力净额。
- 搜索摘要、截图上的无日期数值、盘后网页抓取时间不能证明对应数据为最终收盘。
- 不把今天新补到的历史数据写成旧推荐当时已知。归档保留firstObservedAt；研究可用它重建公开历史，但不能冒充当时实时决策复现。

如果公开源和本地原始档案均无法恢复某日，保留可见缺口。该股票仍可做量价/事件研究，但需要完整资金的策略保持待核验；“全部历史已修复”的验收不能通过。

### 7.3 完整区间的四条恢复路径

按“当前可请求的历史、现有原始档案、可核验历史页面、合法导出”依次尝试，不无限枚举未公开接口。路径可以提供互补证据，但不同统计口径不拼成一个连续序列。

| 路径 | 具体动作 | 本轮已知状态 | 完成条件/停止边界 |
| --- | --- | --- | --- |
| A 公开历史接口 | 对东方财富/新浪先做小样本契约验证，记录最早/最晚可取日；按真实分页或范围能力回补 | 正常历史链路失败；访客空值/偶有单日 | 取得目标日期原始行并通过校验；不支持范围即停止猜start/end参数 |
| B 本地旧原始档案 | 列出缓存、`.bak`、`.legacy-*`、`.tmp`、报告输入与修订、推荐账本，检索两个代码的资金字段 | 已抽查部分文件无日行，尚未完成全清单审计 | 恢复明确日期、单位、来源的原始日行；全清单逐文件说明命中/无命中/解析失败/未扫描 |
| C 公开历史页面 | 追查F10表格、内嵌数据及页面实际发布的历史导航；检索旧页面只能定位，不直接当最终原始数据 | 光洋出现买入期旧数据线索；吉华无合格样本 | 保存可核验完整表/原始JSON、口径及版本；无旧日期入口则不能假设可任意翻到过去 |
| D 合法导出 | 若用户已有终端可合法导出日资金，导入CSV/HTML原表并核验字段及范围 | 尚无提供的导出文件或服务账号 | 数据真实可核验才补齐；不购买服务、不使用网上示例密钥、不自动登录或绕过限制 |

每一条缺口都要有已尝试路径和下一步，而不是统一写“接口未提供”。没有可用公开入口、旧档案或合法导出时，任务为`blocked-data`，完整恢复仍未完成；不要继续高频请求，也不要暗中改成未来累计N天后算完成。

### 7.4 旧档案恢复必须读取证据，而非展示摘要

复用项目已有`stream-json`、worker隔离和原子写入，不新增爬虫/数据库体系。`lib/large-json.js`的现有展示投影会删除部分路径并裁剪推荐、持仓字段，不能直接把它的返回值作为“原文件没有资金”的依据。

1. 只在项目已确认的数据目录建立文件清单，不扫描整盘；记录相对路径、大小、mtime、内容哈希及扫描状态。备份/临时文件仅只读，不删除或自动替换在用文件。
2. 在worker内流式识别目标代码及相关资金对象。保留祖先对象的股票代码、交易日和provider上下文，不用全文正则把邻近其他股票资金误配过来。
3. 从原始流提取资金路径，不沿用展示摘要的ignore/projection；先抽样识别结构，再按已验证路径扫描。JSONL按流处理，单行巨型对象也不能无上限JSON.parse。
4. 恢复索引独立落盘。单文件解析失败、截断或预算超限都保留状态与偏移/重扫标记，不能当作“已扫描无记录”。崩溃worker由父进程收敛错误，不能再触发未捕获内存异常。
5. 扫描时文件仍变化则标`changed-during-read`，延期重扫或使用已存在的稳定备份；不把两次写入拼接为一个证据文件。哈希相同的副本只解析一次，但保留路径关系。
6. 只输出小批候选至主写入方；大文件读取器的单对象组装、队列长度也需设限，不能把“用了流”当作内存一定有界。

先审计全部相关旧档案再下“本地无法恢复”结论；扫描范围和失败文件必须随恢复结果交付。

### 7.5 历史页字段映射、接续与冲突裁决

- HTML表格按已核验的多级表头映射字段；内嵌JSON只解析已识别的数据段，不执行页面脚本。解析器记录版本，异常列数/未知表头拒绝准入。
- F10适配器明确区分全订单净额、滚动5日主力、当日大单主力；各自存入对应字段。当日数据不能取错为更大或更好看的5日汇总。
- 同源窗口有重叠时逐日核对所有重叠日期；能控制窗口时预留3至5个交易日重叠。少于3日可继续取证但标弱接续；无重叠不能仅凭同域名证明定义一致，须有同一版本契约。
- 同代码、日期、definitionId相同且数值一致的候选去重；不同值进入冲突清单，保留双方证据。不同definitionId不是数值修订，须分开存。
- 收盘价可用未复权日K辅助检查错日、错股、盘中未定稿；对上收盘价只能增强一致性，不能单凭价格选择对应资金值。复权价不得与历史原始报价直接比较。
- 只有明确同源更正/最终版本标识，或从可信同源历史表重新取得并解决冲突，才提升为`historical-final`。不默认“最新抓到/最后一行/最大值”为正确；仍不能裁决就保留冲突，不能计入完整日数。
- 其他provider可以做方向/日期旁证，不能拿不同大单定义的净额相等作为强制验证条件，也不能对两个值取平均。

### 7.6 覆盖证明与交付产物

恢复过程至少展示四个数字：找到线索的日期数、已提取候选日期数、已验证最终日期数、仍缺失/冲突日期数。一次抓到30行，不代表30个有效日；停牌解释与有效资金行分开计数。

每个`rangeId + code + definitionId`输出逐日清单，列出交易日、状态、净额、单位、证据引用、冲突原因、最后尝试及下一步。每日状态为以下之一：`missing`、`candidate`、`provisional`、`conflict`、`validated-final`、`verified-no-trade`。窗口停止原因另记`source-unreachable`、`unsupported-range`、`blocked-data`，不混入每日数据值。

完整判定同时要求：

```text
目标区间已冻结，日历/上市/停牌解释经核验
应有资金记录的每个交易日均为validated-final
同一统计定义，未决冲突=0，未知单位=0，缺失日=0
原始证据可追溯；盘中或检索线索不计入最终覆盖
```

分别报告`有效资金覆盖率`和`日期解释覆盖率`；后者包含核验停牌，不可宣传为100%资金行。若应有记录日数为0，显示不适用，不算100%。多源各自缺日但并集齐全时仅称“跨源证据齐备”，不标同源历史完整。

计划交付本地`recovery-manifest.json`、逐日覆盖CSV及简明恢复摘要，复用现有查看/导出方式，不新建报告服务器。验收页逐股列出：上市以来逐年覆盖、买入以来、买入前窗口、最近10日的覆盖、证据、剩余缺口及恢复条件。不得只给总体成功率。

多年间若供应商分类标准变更，按definitionId分段保留原值及有效日期。分段日期全部核验齐全可标“全历史日期证据齐全，存在口径断点”，但不等于上述`complete`的同口径序列；另设`dateCoverageComplete`与`comparableSeriesComplete`，分别说明日期完整性与可比性。跨断点净额累计、连续流入及统一评分禁用，除非另有可验证口径映射；不能为追求单一曲线而改写原始金额。

### 7.7 恢复后如何回到两股推荐复盘

按买入前、持仓初期、首轮拉升、回撤、再次转强分段展示同源净额、流入日占比及资金/价格背离；量价和消息仍独立核验。未完整分段只能展示已知日，不能据部分正流入推断持续吸筹。

本次补得的数据可用于事后解释，但不得把`firstObservedAt`回填到8月。只有原始推荐时实际保存且在当时可得的证据才能用于实时决策重放；否则标“事后历史重建”。是否改善推荐须在更广、包含亏损和未触发样本的独立区间验证，不能以两只盈利股票倒推增加资金权重。技术恢复验收与选股收益验收分开。

## 8. 调度、性能和每日留存

### 8.1 控制重复失败

第一版工程默认值可配置但不参与策略拟合：

- 同端点最大2个在途请求，全资金任务最多4个；同代码同目标窗口共享Promise，10日请求可复用包含它的90日合格结果。
- 每次provider尝试总预算5秒，包含连接、响应体、允许的重定向；每批交互查询预算10秒。超时真正abort，不仅Promise.race后让底层继续运行。
- 连续3次传输失败进入60秒冷却，之后最多一个半开探测；继续失败延长至5分钟。HTTP429尊重Retry-After，403/登录墙/验证码不重试绕过。
- HTTP200空业务响应按“代码+端点+窗口”负缓存10分钟；源返回1日只记能力不足，不算网络失败，也不算成功补齐。避免某只停牌/不支持股票熔断全部股票。
- `force`绕过普通数据TTL，不绕过安全冷却、合并请求及并发上限。手动重试仅允许一个诊断探测，不让所有股票再次重试一轮。
- 最终历史记录读本地，盘中数据独立短TTL；成功记录不因下一次失败被空结果覆盖，partial补采不降级已有final。

主进程协调请求和写入；market worker通过现有消息通道发资金请求/取消，返回紧凑结果。保持主线程只做异步I/O和小对象转换，不把网络请求迁回同步UI计算。模块级Map只对当前线程生效，必须有跨worker并发及写入测试；不新增常驻服务。

### 8.2 与原收盘报告协调

- 保留每日15:30报告的原约定；15:30开始资金留存任务。若资金源结算未完成，报告明确pending，不阻塞报告无限等待。
- 参考已查网页历史模块标注16:05，安排16:10一次复核，但这只是初始任务时点，不代表所有provider在16:05已完成。日期/phase验证仍是最终依据。[东方财富个股资金页](https://data.eastmoney.com/zjlx/603980.html)
- 后续可重试一次或次日启动补采；日历、收盘判断复用现有实现，不在非交易日造日记录。
- 只有取得有效新数据才生成报告新修订；旧版本与输入证据保留，浏览器查看按已有报告服务处理，不重写收益基准。
- 软件关闭后无后台进程；下次启动从manifest补齐任务。关闭会话前取消请求并完成已接受小批次原子写入，未完成任务保持pending，不能标成功。

## 9. 消费端与提示

资金分析消费能力分级：

| 能力 | 允许使用 | 禁止使用 |
| --- | --- | --- |
| 完整同源最终逐日 | 合格窗口净额、连续流入、流入天数、分段变化 | 推断机构真实身份 |
| 部分逐日 | 明确列出的日期/数值、已知日数 | 输出完整10日结论或跨缺口连续性 |
| 真实多日汇总 | 对应窗口净额及来源明确的比例 | 拆成每日或流入天数 |
| 当日盘中 | 当日累计读数和时点 | 历史替代、收盘确认 |
| 量价代理 | 独立量价压力分析 | 冒充主力资金或填补日资金列 |

大盘、个股、收藏、模拟持仓和报告共用同一能力结果；不再由每处单独根据available判断。已有资金评分若依赖比例/完整性错误，修复时需冻结旧版与新版结果说明变化，不静默回改历史评分。

界面只显示简短状态及详情入口，例如“逐日资金7/10日，缺3日；多日汇总可用”“历史补采进行中；最近尝试失败，下一次09:58”。保留常驻/悬浮提示，不挤动布局；不是每只股票弹一次错误。错误日志记录详细信息，界面不新增滚动日志区。

每日诊断摘要记录请求数、合并/缓存命中、熔断次数、完整/部分/未知代码数、缺口变化、provider成功率、耗时分位数与停止原因。响应正文不反复写入普通日志，避免几十MB失败日志继续膨胀。

## 10. 落地顺序与验收

| 阶段 | 改动边界 | 必须交付的证据 |
| --- | --- | --- |
| P0 完整区间审计 | 冻结两股区间、只读旧档案清单、公开页取证 | 逐日缺口基线、文件扫描覆盖及F10冲突样本；不能只做未来归档 |
| P0 诊断/止损 | 资金请求链、结构化错误、负缓存、熔断和请求合并 | 故障源不会对每股票持续多次重试；10秒交互预算可取消，UI仍响应 |
| P0 数据契约 | 日期、单位、比例、日/汇总/盘中区分 | 固定样本解析和异常夹具通过，陈旧10行不能complete |
| P1 原始档案 | 紧凑历史模块、主写入方、原子持久化 | 重启、并发、断点恢复不丢成功记录，不混不同源 |
| P1 公开源准入/历史恢复 | 现有适配器修复与经验证的新适配器；先两目标，再收藏/持仓 | 每只代码覆盖清单、公开源真实样本、剩余不可恢复日期 |
| P1 留存与报告 | 现有收盘/启动补任务、报告修订 | 当日累计不重复相加、pending真实显示、关闭无驻留 |
| P2 策略接入 | 共用能力消费者，不改选股阈值 | 完整资金可启用对应判断；缺失仍不误发许可；前后评分差异可解释 |

建议把纯解析、覆盖判定与资金档案读写集中到一个小模块（如 `lib/fund-flow-history.js`），网络调用继续复用现有main入口；只有实际复用复杂性出现才进一步拆分。不要顺带重构庞大的main.js或新建通用数据平台。

### 必测清单

1. HTTP200/rc100、Service not valid、HTML、截断JSON、JSONP、超时、连接重置、429均分类正确；无eval、无无限重试。
2. 金额0、负金额、万元/元、0.3%/30%按源契约处理；未知单位进入隔离，不猜数值。
3. 10条旧数据、重复日期、缺交易日、未来日期、盘中未收尾行均不能误判完整；停牌、新股、节假日说明正确。
4. 昨日10日最终序列在今日盘中仍有效；今日资金独立，不为匹配今天而丢掉完整历史。
5. 三日汇总不冒充三行；跨源缺口不拼连续性；净占比不同分母不能混用评分。
6. 600704过去仅1日的响应夹具不能通过10日验收；两个目标空返回不能被当前单点或量价填齐。
7. 两个worker与详情同时刷新同一代码合并请求；force尊重冷却；取消后无遗留网络任务/错误弹窗。
8. 同日重复累计快照只更新版本不相加；final不能被partial覆盖，修订前值和时间保留。
9. 一次写入中断、备份恢复、主进程关闭/重启不丢已成功日期；巨型旧账本恢复任务内存有界、可取消。
10. 15:30未就绪不伪称收盘资金完成；16:10仍未就绪继续pending，次日补采不冒充当时已知。
11. 缺资金窗口不输出吸筹确认/连续流入；大盘、详情、收藏、持仓、报告口径一致。
12. 沪深样本分时点实测，失败保留原始错误摘要；完整单测、UI及报告导出回归后才交付代码。
13. 光洋08-13示例的总资金、5日主力、当日主力分别解析；09-14两组冲突不能last-write-wins，也不能按收盘价直接裁决资金。
14. 旧网页线索、本机ECONNRESET、随后页面超时并存时，不能标在线源健康或历史恢复完成；受限API文档不自动进入调用链。
15. 大文件证据位于展示投影裁掉的字段时仍能从原始流命中；重复备份、单行巨型JSONL、截断及扫描中文件变化均不产生假完整。
16. 光洋部分恢复、吉华缺失时分别计数；买入以来完整但上市早期缺失时，不能把全历史标完整；上市起点未知或无预期交易日不显示100%。
17. 跨provider并集齐全不冒称同口径完整；旧快照的采集时点/文件mtime不变成当年推荐已知时间。
18. 跨年分页、证券更名、长停牌及统计口径变更不会漏日、串股或错误累计；年度文件重启续采和超120日保留均通过。年份不可恢复时不缩短总目标、不清零缺口。

### 实际数据成功标准

- 两目标各自上市首个交易日至目标已结束交易日逐日覆盖逐项可核验，无来源不明/估算伪装/盘中冒充最终值；达不到就明确未完成全历史恢复。
- 上市以来全区间、买入以来、买入前窗口、最近10日分别验收；一个成功不能代替另一个。存在口径断点时单独披露，不以日期覆盖齐全冒称可跨期比较。
- 从启用后实际取得的收盘/最终资金能跨重启持续留存；新产生缺口有明确原因和有界补采任务。
- 若外部源仍阻塞，可以交付工程修复及真实部分恢复，但不能宣布“历史逐日资金问题已全部解决”。
